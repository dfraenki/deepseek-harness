# Agent Note: Agentic software factory — self-replication, mutation loop, and plugin synthesis

Status: proposed

English | [中文](2026-11-27-agentic-software-factory.zh.md)

## Problem

Artifork today is an assistant over external worktrees: the agent edits other repositories while this repository's own code, UI, and plugins are static from the model's point of view. Turning the harness into a different application — "become an intuitive electronic-music production DAW" — still requires a human to fork, rebrand, re-compose plugins, and keep the build green. Three capability gaps follow from the current architecture. First, no self-cloning: nothing can copy the factory's own minimal core into an isolated directory and boot it as an independent application. Second, no unattended transformation loop: `tool-ralph` ([README](../../../../packages/experimental/tool-ralph/README.md)) already runs fresh-agent rounds toward one immutable objective with structured handoffs, but nothing wires that loop to a goal file that describes a whole target application, to real build/test verification of each milestone, or to git checkpoints with rollback. Third, no first-class path from a multimodal brief — natural language plus screenshots of reference applications — to a set of Cordis plugins that re-compose the product, even though the composition-patch mechanism this needs already exists ([ralph-bundle's `cordis.patch.yml`](../../../../packages/experimental/ralph-bundle/cordis.patch.yml)) and the identity-mutation playbook has just been rehearsed manually by the Artifork rebrand.

## Proposal

Build the factory as five layers, each mapped onto an existing seam rather than a new runtime. The layers are separable: each is useful alone and shippable as its own experimental package, following the ralph-bundle pattern (shipped switched off, hidden from default plugin lists).

1. **Goal ingestion (multimodal).** A `MUTATION_GOAL.md` at the clone root defines the target application: identity (name, tagline, brand direction), domain, experience narrative, feature list, ordered milestones with executable acceptance checks, whole-app acceptance criteria, and references. Reference material — screenshots, mockups, competitor app notes — lives in `references/` next to it; vision-capable models already ingest images through the existing LLM stack, and the loop's first rounds convert each reference into a structured analysis file in the workspace, which is the round-to-round memory per the ralph workspace-as-authority contract.
2. **Isolated spawn (`spawn_and_mutate`).** The factory never mutates itself. Spawning copies the running checkout into a target directory (local `git clone`, fresh history), assigns an independent `DSH_HOME`, server port, and database, and writes `MUTATION_GOAL.md`. Version 1 clones the full monorepo and re-composes what the clone *runs* through a generated mutation profile patch (`cordis.patch.yml` shape) instead of deleting packages: build integrity is preserved by construction, and pruning to a minimal core becomes an optimization only after spawn and loop are proven. A plugin (new experimental `factory` package) owns this capability; a model-facing `spawn` tool exposes it.
3. **Mutation loop.** A `factory-bundle` profile mounts the loop on `tool-ralph`: the immutable objective is the content of `MUTATION_GOAL.md`, each round is a fresh agent that implements the next milestone as plugins, and the bounded handoff carries milestone status, verification results, and the next approach. Ordinary progress tracking stays with the goal tools ([goal-round-driver](../../../../packages/goal/goal-round-driver/README.md)) so the mother factory can observe the clone's run without interfering.
4. **Verification and git autopilot.** Every milestone must pass real gates inside the clone before it counts: library build, typecheck, targeted tests, and a headless boot smoke of the web profile. Green milestone → automatic `git commit`. Three consecutive failed attempts on the same milestone → `git reset --hard` to the last green commit, and the failed approach is recorded in the workspace so the next round tries a different one. The loop stops only when every acceptance check in the goal file passes.
5. **Plugin synthesis.** Every new capability of the target application lands as a first-class Cordis package with both faces (tool and client), locale keys, tests, and a bilingual README pair, mounted through the mutation profile patch — the clone stays an everything-is-a-plugin application at every point of its transformation, and the agent's tools and the UI grow together. Identity changes (name, mark, titles, locales) reuse the rebrand playbook proven by the Artifork rebrand.
6. **Shared live preview.** The clone's web app runs as one preview instance on its isolated port, embedded in a mother-side client plugin surface (a slot occupant, not a separate app) so the user watches the transformation in real time — dev-server HMR between gates, freshly built output for each gate verdict, an explicit run header naming the current milestone and its status. The clone's agent verifies and probes that same instance through its browser-use session ([browser-use-playwright-mcp](../../../../packages/experimental/browser-use-playwright-mcp/README.md), [browser-use-stagehand-native](../../../../packages/experimental/browser-use-stagehand-native/README.md), with [inspector](../../../../packages/experimental/inspector/README.md) for console and network evidence), which makes the boot-smoke and UI-assertion gates apply to the exact instance the user is watching. The frame is cross-origin to the clone's port and carries no mother-side credentials: the clone is untrusted code.

7. **Rehearsal on the mother (practice, distill, fork).** Because the mutation agent modifies the harness using the harness itself, the first attempts at any new capability happen on the mother, not on a clone: the agent experiments with alternative ways to build it (plugin shapes, UI slots, tool contracts), and git makes every failed experiment disposable while the mother stays pristine. Each validated approach is distilled into a factory skill, so the factory learns to modify itself by modifying itself — every transformation makes the next one better. Only when the path toward the goal is rehearsed does the agent call `spawn_and_mutate` with a goal file already refined by that practice; the clone inherits the distilled skills because they are part of the repository it receives.

8. **Coaching layer (three observers).** A `factory-observers` plugin mounts three read-only coach subagents beside the mutation agent. The process coach watches how the agent works (tool calls, repeated failures, skipped gates, wasted rebuilds) and produces execution optimizations; the intent coach watches the human's messages against the immutable goal and produces direction refinements; the skill master watches everything, curates which skills reach the agent — researching plugin-creation knowledge and authoring new skills into the clone's `.agents/skills/` when it detects a gap, which the watched skill filesystem provider then delivers automatically — and is the only coach allowed to stop the agent, through a fixed escalation ladder: directives first, a pause at the next round boundary (a flag the loop driver honors before starting the next round), and a mid-round cancel only on strong evidence such as a directive already covering a failure the agent is repeating. Coaches never execute project code and never touch the goal file; a deterministic governor merges their proposals into one size-capped, evidence-backed directive section applied only at round boundaries, with same-topic supersede and full trajectory visibility. Validated directives are distilled into factory skills when the run ends, so the next clone inherits what this one learned.

The factory's own code follows the same rules as everything else: the spawn service, the mutation profile, the verification harness, and the preview surface are plugins with tests, coverage-gated, documented in paired READMEs.

## Alternatives considered

- **External orchestrator script (shell/Python) driving `dsh` headless.** Rejected: it duplicates the loop logic outside the plugin architecture, loses model-visible logging of every step, and would make the loop un-configurable per deployment. The ralph loop already solves round structure, handoffs, and budget ceilings.
- **Mutating the factory in place with worktrees.** Rejected: `tool-worktree` covers parallel in-repository work, but self-replication needs a different blast-radius boundary. The mother must stay pristine so a failed mutation never damages the tool that has to repair it; clones give that isolation with their own history, home, port, and database.
- **Deleting non-core packages at spawn time to produce a minimal clone.** Deferred: deleting packages risks breaking reference graphs and build gates the loop itself depends on. The profile-patch composition achieves the same running surface with none of that risk; pruning is a later optimization with its own verification story.

## Acceptance criteria

- A spawned clone boots the web profile headless from a clean directory, on its own home, port, and database, without touching the mother's state.
- A toy mutation ("become X": identity change plus one new plugin) runs end-to-end unattended: goal file → rounds → green build, typecheck, tests, boot smoke → automatic commits.
- Rollback is exercised in that run: an injected failing milestone causes three attempts, then `git reset --hard`, then a different approach that lands.
- The clone's final tree still passes the repository's own gates (coverage on new packages, pairing, lint), because the loop reused those gates as its verification.
- The mother factory's tree is byte-identical before and after any clone's mutation run.
- During a run, the user's preview and the agent's verification address the same instance: a milestone marked green has a recorded gate run whose UI assertions were executed against the instance the user can open, and the run header names that milestone.
- A rehearsal round for a new capability runs on the mother, ends with the mother's tree byte-identical (failed experiments are git-disposable), and lands at least one distilled skill before the matching `spawn_and_mutate` call.
- During a mutation run, every accepted coach directive cites observable evidence, fits the size-capped section, and is visible in the trajectory; the skill master's boundary pause halts the loop before the next round, reconfiguration updates skills, and the loop resumes without losing milestone state.
- All new packages ship switched off by default and are documented in bilingual README pairs with recorded consistency entries.

## Risks

- **Unattended code execution.** The loop runs with code-execution capabilities and no per-step human approval; a mutation loop that escapes its clone directory or its resource limits damages the host. Mitigation: spawn-level sandboxing of the clone's working directory, the existing approval policy for the mother, and the loop refusing any path outside the clone root. SAFETY.md's experimental-status language extends to this feature verbatim.
- **Verification theater.** A loop that trusts its own claims ("tests pass") without running the gates will drift into broken states confidently. Mitigation: the autopilot runs the gates itself and parses their exit codes; a milestone is green only on a green gate run, never on a report. The shared preview sharpens this: the user sees the same instance the gates exercised.
- **Untrusted preview.** The embedded clone app is model-written code shown in the factory's UI; its frame is cross-origin, carries no mother-side tokens, and its surface labels unverified states as such. A preview that dies or hangs is a reported red gate, not a blank frame.
- **Cost and runtime.** Fresh-agent rounds with full rebuilds per milestone are expensive; a DAW-scale goal may need hundreds of rounds. Mitigation: milestone granularity is an authoring rule of the goal skill (small, compilable, independently verifiable), and the loop's budget ceilings come from the existing ralph config.
- **Coach interference.** Coaches that fight each other, over-tune the agent mid-round, or drift into running the project themselves destabilize the loop. Mitigation: one deterministic governor with topic supersede, boundary-only application by default, a fixed escalation ladder where only the skill master may pause or cancel, and budget-capped observers that cannot execute project code.
- **Upstream drift.** This fork already diverges; the factory deepens divergence from upstream `deepseek-ai/deepseek-harness`. Accepted deliberately: the factory's value is the divergence, and the two-layer naming strategy (Artifork product surface, `dsh`/`DSH_*` protocol identifiers) keeps upstream references navigable.
